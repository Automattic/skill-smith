## Issues

### Issue 1: Task 11 omits `src/pipeline/pipeline.ts` from its "Files to change", yet the run-wide judge mutex must be created and injected there

**What's wrong:** Task 11's prose says the judge-concurrency mutex is "scoped to the whole run/iteration, shared across **both** the scenario-level `Promise.all` (in `pipeline.ts` / `runScenario`) and the agent-level `Promise.all` (in `agent-loop.ts`)" and instructs to "thread it through `RunAgentsParams` → `RunAgentPairParams`." But the task's **Files to change** list contains only `agent-loop.ts`, `judge-agent.ts`, `config/types.ts`, and `config/normalize.ts`/`validate.ts` — **`src/pipeline/pipeline.ts` is not listed**. In the codebase the scenario-level fan-out lives in `pipeline.ts` (`Promise.all(args.selection.map(s => runScenario(s, {...})))`, ~line 384, inside the per-iteration function), and `runScenario` is the caller of `runAgents` (~line 511). To get one run/iteration-wide lock shared across both fan-outs, the mutex must be **instantiated once in `pipeline.ts` above the scenario `Promise.all`** and passed into each `runScenario` params object (lines ~387–396), which then forwards it to `runAgents`. A writer scoped strictly to Task 11's file list would not edit `pipeline.ts`. The dangerous failure mode is that the writer instead creates the mutex *inside* `runAgents`/`runScenario` (per-scenario or per-agent-loop), producing a **per-scenario lock rather than the run-wide bracket lock** the design fixes as load-bearing (design "Judge concurrency knob": "one lock shared across all pairs in the iteration, not per-scenario"). That would silently fail to prevent the cross-scenario `wp-env start` race the knob exists to stop (R4/R7).
**Where in plan:** Task 11, "Files to change" (missing `src/pipeline/pipeline.ts`) vs. its "Changes"/"Acceptance".
**Suggestion:** Add `src/pipeline/pipeline.ts` to Task 11's Files to change, and pin the mutex's instantiation point: create the shared async mutex once per iteration in `pipeline.ts` (above the scenario-level `Promise.all`), thread it through the `runScenario` params object → `RunAgentsParams` → `RunAgentPairParams`, and have every pair acquire that same instance. State explicitly that the mutex is constructed exactly once per iteration (not per scenario, not per agent loop), so the lock is genuinely run-wide.
**Why it matters:** The file list is the authoritative per-task surface for the code-writer. Omitting the file where the lock is created and injected leaves the most subtle, correctness-critical wiring (run-wide vs. per-scenario scope) unpinned — the exact place where the design says getting the scope wrong reintroduces the shared-env cross-talk the whole concurrency feature is meant to eliminate.

### Issue 2: Task 13 calls judge user-message file inlining "optional," but the mock-gated self-improvement-loop test depends on it, so dropping it breaks the `npm test` gate

**What's wrong:** Task 13 instructs rewriting `buildUserMessage` and says "file inlining is optional; keep at most a lightweight pointer line to the judge workspace path (**or omit inlining entirely**)." However, the deterministic mock judge gates on the *content* of the produced workspace file: `invokeJudge` in `src/providers/mock.ts` returns PASS/FAIL based on `params.prompt.includes('GATE_PASS')` / `'GATE_FAIL'` (mock.ts ~lines 107–110), and the gated testing agent writes that token into `result.txt`. The only path by which `GATE_PASS`/`GATE_FAIL` reaches the judge prompt is `buildUserMessage` inlining the workspace files. If a writer takes Task 13's "omit inlining entirely" option, `self-improvement-loop.test.ts` — a mock-based deterministic test that is part of the `npm test` gate (it passed in my run) — would no longer flip from FAIL to PASS after the marker propagates, breaking `npm test`. This puts Task 13 ("inlining optional") in direct tension with Task 14's acceptance ("The gated self-improvement-loop behavior (GATE_PASS/GATE_FAIL) still drives a pass after the marker propagates") and with the `npm test` gate every task must keep green.
**Where in plan:** Task 13, "Changes" (buildUserMessage) and "Depends on"; Task 14 acceptance (third bullet).
**Suggestion:** Remove the "or omit inlining entirely" option and require Task 13 to keep inlining the produced workspace files into the judge user message (the `GATE_*` token must remain reachable), or, if inlining is to be dropped, explicitly change the mock's gate seam in Task 14 to key off something still present in the judge prompt/cwd. Make the chosen approach a per-task constraint so two writers produce the same result and the gated loop test stays green.
**Why it matters:** As written, two writers could make opposite, both-"plan-compliant" choices, one of which fails the shared test gate. The acceptance criteria backstop it eventually, but the plan should not contain an option that is known to break a fixed gate — pin the behavior so the writer doesn't have to discover the dependency by trial.
