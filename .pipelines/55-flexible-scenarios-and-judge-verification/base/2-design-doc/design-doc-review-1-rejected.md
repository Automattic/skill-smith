# Design Doc Review

## Verdict: rejected

## Summary

This is a strong, well-researched design doc. Almost every load-bearing claim was verified true against the actual codebase: the `classifyVerdict` FAIL-notes fix (`src/reports/verdict.ts:30-50`), the verbatim `{ pass, notes }` flow through `aggregateScenarioReport`/`projectReportForImprover`/`collectSkillIds` with no rework (`src/improvement/context.ts:110,136`; `src/reports/scenario-report.ts:79,93`), the open agent-key passthrough that capabilities ride (`AgentDefinition[key:string]:unknown`, codex `extraThreadOptions` at `src/providers/codex.ts:167-181`), the read-only judge surfaces (`TOOLS_BY_ROLE`/`SANDBOX_BY_ROLE`), the awaited fire-and-forget `beforeJudgeAgent`/`afterJudgeAgent` hooks with the right `AgentContext`, env-var visibility via `claudeCodeEnv(process.env)`, the Codex `approvalPolicy:'never'` + `read-only` exec risk (honestly flagged as R1), and "zero dangling reads" to the trimmed `Scenario` fields (grep-confirmed). Spec coverage is complete and the matrix is faithful. The doc stays at design altitude. There is, however, one substantive soundness gap in a load-bearing decision: the judge-concurrency knob, as specified, does **not** make the design's own primary example (`testing-project`'s single shared wp-env) safe, because the env lifecycle lives in the hooks that bracket — but are not part of — the judge call. Two concurrent pairs would still race on `wp-env start` regardless of the knob. That one issue, detailed below, is the reason for rejection. Two smaller accuracy/consistency notes follow; they are not independently blocking but should be corrected in the same pass.

## Issues

### Issue 1: The judge-concurrency knob, as specified, does not serialize the shared-environment lifecycle it is meant to protect

**What's wrong:** The design rests the correctness of the shared-environment case on a concurrency knob whose stated semantics are too narrow to actually hold. The doc commits to two facts that are individually true but jointly insufficient:

1. The knob "runs judge **calls** one at a time (testing agents still parallelize via `Promise.all`)" — i.e. it serializes the judge *invocation* (`runJudgeAgent`). (Design: "Judge concurrency knob"; Key Decision "Keep the judge per-(scenario, agent)…".)
2. In `testing-project`, the WP env is **started in `beforeJudgeAgent`** (build plugin, boot wp-env on the fixed port 8987, activate, create a post) and **stopped in `afterJudgeAgent`**. (Design: Key Decision "`testing-project` — per-pair WP env…"; End-to-end data flow steps 4–5.)

The codebase runs the pipeline with **two-dimensional parallelism**: `Promise.all` over scenarios (`src/pipeline/pipeline.ts:384`) *and* `Promise.all` over agents within each scenario (`src/pipeline/agent-loop.ts:94`). The `beforeJudgeAgent` → `runJudgeAgent` → `afterJudgeAgent` sequence lives inside `runAgentPair` (`agent-loop.ts:224-276`), nested under both fan-outs. Because the env up/down is in the **hooks** and not in the judge call, serializing only `runJudgeAgent` lets two concurrent pairs both enter their `beforeJudgeAgent` hooks and both run `wp-env start` on the same `WP_ENV_HOME`/port 8987 before either judge call acquires the serial lock. That is exactly the cross-talk the design cites as fatal: vanilla wp-env keying by project path means "a second start rewrites the first's wp-config" (Risk R7, confirmed against `testing-project/eval/utils/verify-e2e.ts:117-135`, which writes a single project-root `.wp-env.json` on a fixed port). So the serial-judge knob as described does not prevent the very race it is introduced to prevent.

For the critical section to be correct, the serialized unit must be the whole **`beforeJudgeAgent` + judge + `afterJudgeAgent`** bracket (env-up → verify → env-down), not just the judge invocation. The design never says this, and an implementer reading "serialize judge calls" literally would build a still-racy system.

This is a consistency conflict between two committed decisions, not a deferred detail. The doc defers only the knob's *config key name and placement* ("exact config key/placement is a plan-phase detail"); it does not defer *what gets serialized*, which it states as a fact. The doc's own claim — "This lets a project that uses one shared live environment avoid cross-talk" — is therefore incorrect as written.

**Where in design doc:** "Interfaces and Data Flow → Judge concurrency knob"; "Key Decisions → Keep the judge per-(scenario, agent); env via project hooks; add a serial/parallel concurrency knob"; "Key Decisions → `testing-project` — per-pair WP env in `beforeJudgeAgent`, serial judges…"; "Failure Modes and Observability → Shared env + `parallel` judges". Maps to Requirements 6, 10 and Acceptance 5.

**Suggestion:** Make the serialized critical section explicit and correct: when concurrency is `serial`, the harness must hold the serial lock across the entire per-pair judge bracket — `beforeJudgeAgent`, the judge invocation, and `afterJudgeAgent` — so the project's env-up/verify/env-down runs uninterleaved with any other pair's. State this in the concurrency-knob description and in the `testing-project` decision, and reconcile it with the "testing agents still parallelize" sentence (the testing phase is unaffected; only the judge bracket is gated). Note this also resolves the implicit question of whether the gate spans both the scenario-level and agent-level `Promise.all` fan-outs — it must span both. If the writer intends instead to keep the env shared across the whole iteration, that path is already ruled out by the doc's own R6 timing argument (artifacts don't exist at `beforeAllScenarios`), so the per-pair bracket-serialization is the remaining coherent option.

**Why it matters:** This is the load-bearing decision for the no-WP-in-core, project-owned-env story (req. 10) and for the judge actually verifying behavior on a live environment (req. 6, Acc 5). As written, two implementers would diverge — one serializes only the judge call (racy, silent wp-config corruption, flaky/false verdicts), one serializes the bracket (correct) — and the doc points at the wrong one. Even under req. 16's "one scenario × one agent" pipeline posture, the design explicitly sells this knob as the mechanism that makes full *manual* shared-env runs safe, so the gap surfaces precisely on the documented full-run path.

### Issue 2: The `# Skills` "first heading wins" rule contradicts the "any heading depth" collection rule for nested headings

**What's wrong:** The `# Skills` parsing rules say: (a) match the first heading `^#{1,6}\s+Skills\s*$` at *any* depth, then (b) "collect lines until the next heading **of any depth** (`^#{1,6}\s`)." These two rules interact badly for a brief that legitimately nests content under Skills. If an author writes a sub-heading inside the Skills section (e.g. `# Skills` followed later by `## Notes` with the actual list under it, or any `##` subsection), collection stops at the first nested heading and silently drops the list items beneath it — producing a wrongly-empty or wrongly-truncated `skills` set with no error (empty section is "valid"). Because the section is otherwise opaque prose, this is a silent-miss failure mode: the scenario enumerates clean but the testing agent loads the wrong skill set. The design accepts "any heading depth" for the *Skills* heading itself specifically so nesting isn't penalized, but the termination rule then penalizes any nesting *within* the section. The two rules are not internally consistent about how nesting is treated.

**Where in design doc:** "Interfaces and Data Flow → `# Skills` parsing rules" (and the mirrored list in "Key Decisions → Hand-rolled `# Skills` parser"). Maps to Requirements 3, 4 and Acceptance 2, 3, 4.

**Suggestion:** Either (a) restrict the terminator to a heading at the **same-or-shallower depth** as the matched Skills heading (so sub-headings inside the section don't terminate it), or (b) explicitly document and accept that the Skills section ends at the next heading of any depth and that authors must keep the list flat with no sub-headings — and, if (b), state how a non-empty-but-truncated parse is surfaced (it currently would not be). Pick one and make the rule self-consistent so two implementers parse the same brief identically.

**Why it matters:** This is the *only* structure Skillsmith still parses, and a silent wrong-skill-set undermines the first-class "skills are what Skillsmith tests and improves" guarantee (req. 5) with no error path. It directly affects whether two independent implementations of the parser agree.

### Issue 3 (non-blocking note): minor source-location and helper-shape inaccuracies to tidy

**What's wrong:** Two small accuracy slips that don't change the design but should be corrected so the plan phase doesn't chase them:

- The doc implies `snapshotWorkspace`/`diffSnapshots` are reusable shared helpers ("reuse the existing `snapshotWorkspace`/`diffSnapshots`"). They actually live as **private, unexported** functions inside `src/pipeline/testing-agent.ts` (snapshot/diff over `{ mtimeMs, size }`), not in a shared util. To "reuse" them for the agent-loop diff-guard they must first be extracted/exported — a real (small) refactor the doc presents as a no-op reuse. Worth naming as a tiny new-component step rather than pure reuse.
- The enumeration error text for an unknown skill id is shown as `"unresolved reference: skill \"<id>\""`, but the current code concatenates **all** missing references into one comma-separated string (`unresolved reference: skill "x", rubric "y"`) via `missing.join(', ')` (`src/scenarios/enumerate.ts`). After rubrics are removed the message is skills-only, but it's still a joined list (e.g. multiple unknown skills), not the singular form quoted. The "multiple problems concatenate into one `error` string" note elsewhere is correct; the quoted single-id example just under-describes it.

**Where in design doc:** "Components → New (core, small) → A workspace-copy helper"; "Dependencies → Internal"; "Interfaces and Data Flow → Enumeration error strings".

**Suggestion:** Note that the snapshot helpers need extraction from `testing-agent.ts` before reuse, and phrase the unknown-skill error as a joined list of unresolved skill ids. These are clarity fixes; on their own they would not warrant rejection.

**Why it matters:** Keeps the plan phase from treating an extraction as free reuse and from asserting an exact error string the code doesn't currently emit. Low stakes, but cheap to fix in the same revision.
