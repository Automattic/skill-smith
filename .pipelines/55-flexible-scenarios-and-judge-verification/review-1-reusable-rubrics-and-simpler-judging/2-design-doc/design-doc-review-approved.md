## Fresh adversarial pass (no blocking findings)

- **Feasibility — Track A.** Verified `parseSkillsSection` (`enumerate.ts:41–70`) cleanly separates `HEADING_RE` from the `SKILLS_HEADING_RE` heading-text predicate, so factoring a heading-predicate-parameterized helper and exposing `parseRubricsSection` is mechanical; `normalizeSkillId` is id-agnostic. `scenarioFromBriefs` (204–242) builds `problems[]` and validates skills with `existsSync(join(skillsRoot, skill, 'SKILL.md'))`, so the `existsSync(<rubricsRoot>/<id>.md)` mirror and the `unresolved reference: rubric "<id>"` message ride the same channel as designed. Both `scenarioFromBriefs` and `stubScenario` (254–265) build a `Scenario` literal without `rubrics` today — confirming the design's instruction that both must populate the field, and that doing so is exactly what trips the smoke hook. `loadSkill` (`skill-loader.ts`) is a faithful `loadRubric` template; the stated entry-file difference (flat `<id>.md` with link-containment scoped to the rubrics root, vs. `<id>/SKILL.md` scoped to the per-skill dir) is internally consistent. `buildJudgeSystemPrompt` (`judge-agent.ts:150–172`) is a pure `sections`-array builder taking `(scenario, config)`, and `runJudgeAgent` already holds `scenario`, `projectRoot`, and `config` — so resolving the rubrics root and building the blob in `runJudgeAgent`, then passing it as a third builder param, is feasible and keeps the builder filesystem-free.
- **Feasibility — Track B.** The env-once / live-bind-mount / human-language-judge / free-block-name claims rest on `@wordpress/env` 11.4.0 `mappings`, `--config` keying on `md5(configFilePath)`, the claude-code `process.env` passthrough, the serial judge lock bracketing `beforeJudgeAgent → judge → afterJudgeAgent`, and `wp-scripts` copying `block.json` to `build/` with `name` intact. These were all source-verified in design-research and carried into the doc; the design correctly flags the single not-empirically-booted assumption (live bind-mount visibility) as Risk 2 with a manual single-scenario sanity check, consistent with the manual testing posture.
- **Coverage and traceability.** Every requirement and acceptance criterion maps to a Key Decision with an explicit "Traces to" line; the env-once / human-language / free-block-name / conversion tracks each carry their spec links. No requirement is silently dropped and no out-of-scope item creeps back in (per-rubric scoring, parallel judging, runtime swap, generic includes, globally-unique block naming, and backward compatibility are all explicitly held out).
- **Consistency.** The `checkPaths` contract is stated identically in Components (no `rubrics` in the loop), the Key Decision (optional, no default, no existence gate), and Failure Modes (per-scenario unknown-rubric error is the sole failure path). This resolves design-research Open Question 1 to option (b), faithfully. The two-track composition section names the distinct, non-colliding judge-prompt headings, matching the current builder's `# Output format` / `# Recursion guard` / `# Role instructions`.
- **Altitude.** The doc describes architecture, interfaces, data flow, and decisions with trade-offs and alternatives; it names tests and contracts without writing them, and defers writer/plan details (exact heading text, port env-var name, wrapper-vs-cd bridge form) to explicit Open Questions. It does not bleed into a step-by-step implementation plan.
- **Failure modes, dependencies, observability, posture.** Each failure path (unknown rubric id, missing rubrics dir, wp-env boot failure, per-pair install/activate failure, LLM-judge flakiness, teardown failure, guard-test breakage) is named with how it surfaces. No new external dependency. The manual testing posture (deterministic gates green, no full-suite-green gate, no self-improvement loop) is preserved and traced to Req 14 / AC 9.
