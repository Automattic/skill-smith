# Design Doc Review

## Verdict: rejected

## Summary

The design is architecturally sound and faithful to the spec. Both tracks were verified against the real code on the branch and the load-bearing claims hold: the `# Skills` parser (`parseSkillsSection` + `normalizeSkillId` in `enumerate.ts`) is genuinely factorable for a sibling `# Rubrics` parser; the unknown-skill error channel (`scenarioFromBriefs` → `problems[]` → `EnumeratedScenario.error` → keep-but-skip-and-fail-aggregate) is exactly as described and rubric errors can ride it; `loadSkill` is a faithful template for `loadRubric`; `buildJudgeSystemPrompt` is a pure `sections`-array builder receiving `config`; the `Paths`/`Scenario`/`DEFAULT_PATHS`/`checkPaths`/`normalize`/`validate` surfaces match the doc; and on Track B the per-pair `setUpJudgeEnv`/`tearDownJudgeEnv` model, the `deactivateAllPlugins()` clean-slate primitive, the name-agnostic `index.php` glob registration, the deterministic slug, `@wordpress/env 11.4.0` + `@wordpress/scripts 32.2.0`, and the claude-code `process.env` passthrough with `cwd = judgeWorkspace` are all confirmed. The design altitude is correct (architecture, not a task list), the testing posture is preserved, and the Open Questions are genuinely deferrable.

It is rejected for one substantive, correctness-affecting gap: the design's accounting of which **base guard tests break when rubrics are re-added is materially incomplete**, and the design explicitly asserts that accounting is exhaustive. At least three executed guard tests beyond the three the design names will fail when the change lands — including one (the smoke fixture's `afterAllScenarios` hook) that runs inside the `npm test` deterministic gate the design promises stays green. Because "the deterministic gates stay green (including the updated rubric guard tests)" is a load-bearing claim of this design (Req 14 / AC 9), the missing tests must be enumerated and slated for update before the plan phase, exactly as the three named ones are.

## Issues

### Issue 1: The set of base guard tests that break on re-adding rubrics is under-counted; the design claims it is complete

**What's wrong:** The design names exactly three guard tests that pin the base rubric removal and must be updated — `core-types.test.ts`, `check-paths.test.ts`, and `testing-project-e2e-removal.test.ts` — and presents this as the exhaustive set (Failure Modes bullet "Guard tests pinning the base removal"; Decision "`paths.rubrics` is optional…"; the design-research note that it checked for "any OTHER base tests/asserts that re-adding rubrics would break"). A full sweep of `src/__tests__/` for `rubric`/`paths.rubrics`/`scenario.rubrics`/`eval/rubrics` finds **at least three further executed assertions** that the change as designed will fail and that the doc does not mention:

1. **`src/__tests__/fixtures/smoke-project/skillsmith.config.ts:48-59`** — the smoke fixture's `afterAllScenarios` hook iterates `['description','prompt','acceptance','rubrics']` and throws `Scenario must not carry the removed field "rubrics"` if any appears in `scenario.scenario`. This fixture is driven by a **real `run()`** in `src/__tests__/smoke.test.ts:23`, which fires `afterAllScenarios`. The design mandates that `scenarioFromBriefs` and `stubScenario` populate the new `Scenario.rubrics` field (Components → core; "must populate the new `rubrics` field"). Once they do, `'rubrics' in scenario.scenario` is true for every enumerated scenario and the smoke run throws — failing `npm test` (`node --import tsx --test src/__tests__/*.test.ts`), i.e. the deterministic gate. This is the most serious miss: it is not a type-only or filesystem guard, it is an executed end-to-end gate.

2. **`src/__tests__/judge-agent.test.ts:125-138`** (`buildJudgeSystemPrompt carries no rubric/acceptance scaffolding`) — asserts `!/rubric/i.test( prompt )` over the judge system prompt. The design injects the resolved rubric blob into `buildJudgeSystemPrompt`'s `sections` under a heading such as `# Grading rubrics` (Track A, step 3; Decision "Inject the resolved rubric blob…"). Any such heading or blob makes `/rubric/i` match and breaks this assertion directly. (Note also the test feeds a scenario with no `rubrics`, so the builder must tolerate an absent/empty blob — which the design's "when non-empty" guard handles, but the `/rubric/i` assertion itself still fails the moment a rubric-bearing scenario is graded; the test as written will need its intent rewritten to "no rubric *scaffolding* when no rubric is referenced," or similar.)

3. **`src/__tests__/testing-project-scenarios.test.ts:188-229`** (`each JUDGE.md inlines the full rubric, the env-var convention, and live checks`) — for every scenario it asserts the brief **includes** the inlined rubric sentinel (`RUBRIC_SENTINEL`), **does not** reference `wp-interactivity-api-best-practices.md`, and **states** `$SKILLSMITH_JUDGE_URL` / `$SKILLSMITH_POST_ID` / `$SKILLSMITH_PLUGIN_SLUG`. The conversion (Track B) does the exact opposite on all three: it deletes the inlined rubric, references the rubric by id (and the rubric file), and drops `SKILLSMITH_JUDGE_URL` / `SKILLSMITH_POST_ID`. Every assertion in this test inverts.

A fourth, lower-confidence item: **`testing-project-scenarios.test.ts:231-248`** asserts `_candidates.yaml` does not document a `rubrics:` key. `_candidates.yaml` currently contains no rubric mention, so this only breaks if the conversion re-introduces such wording — likely a non-issue, but it belongs in the same guard-test family the design enumerates so the plan can confirm.

**Where in design doc:** "## Approach → Track A" (final paragraph, the "guard tests must be updated" sentence); "## Components → Skillsmith core → Modified → `src/config/types.ts`/`enumerate.ts`" (the "must populate the new `rubrics` field" instruction); "## Key Decisions → Decision: `paths.rubrics` is optional, with no `DEFAULT_PATHS` entry and no `checkPaths` existence gate" (the cost paragraph enumerating the three tests); "## Failure Modes and Observability → Guard tests pinning the base removal."

**Suggestion:** Expand the design's guard-test accounting to the full set so the plan inherits it. Concretely, add to the "guard tests to update" list (and to the Failure Modes bullet):
- `fixtures/smoke-project/skillsmith.config.ts:48-59` — drop `'rubrics'` from the removed-field assertion list (it is no longer a removed field).
- `judge-agent.test.ts:125-138` — restate the "no rubric scaffolding" assertion so it tolerates the injected rubric section (e.g. assert the *absence* only when the scenario references no rubric, or remove the blanket `/rubric/i` ban).
- `testing-project-scenarios.test.ts:188-229` — rewrite to assert the *new* contract (rubric referenced by id, not inlined; the dropped env vars no longer required; the new bridge facts present), mirroring how the doc already plans to flip `testing-project-e2e-removal.test.ts`.
- `testing-project-scenarios.test.ts:231-248` — confirm the conversion does not re-add a `rubrics:` mention to `_candidates.yaml` (or update the assertion if it does).

The design does not need to write these tests — only to name them and state the new contract, exactly as it already does for the three it found.

**Why it matters:** The design stakes "the deterministic gates stay green, including the updated rubric guard tests" as an explicit, traced obligation (Req 14 / AC 9; Failure Modes; Testing posture). If the plan phase is handed an incomplete list, an implementer who updates only the three named tests will see `npm test` fail on the smoke run, `judge-agent.test.ts`, and `testing-project-scenarios.test.ts` — i.e. the very gate the spec uses as acceptance. Worse, the smoke-fixture failure is non-obvious: it surfaces as a thrown `afterAllScenarios` hook deep inside a full run, not as an obvious "rubrics" type error, so an implementer is likely to misdiagnose it. Enumerating the complete set now is the difference between a clean implementation and a stalled one, and it is precisely the kind of "no other base tests break" claim the design asserts but did not fully verify.
