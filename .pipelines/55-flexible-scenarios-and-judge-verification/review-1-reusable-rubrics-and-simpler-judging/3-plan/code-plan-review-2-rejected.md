## Issues

### Issue 1: The `typecheck` gate is red at the Task 1 commit — the `core-types` `@ts-expect-error` flip (Task 2) lands one commit too late

**What's wrong:** Task 1 adds `rubrics?: string` to `Paths` and `rubrics?: string[]` to `Scenario` in `src/config/types.ts` (and only that file). The guard test `src/__tests__/core-types.test.ts` deliberately pins the *absence* of those fields with two `@ts-expect-error` directives: line 76 (`// @ts-expect-error \`rubrics\` is removed from Scenario` over `const _rubrics: string[] = scenario.rubrics;`) and line 95 (`// @ts-expect-error \`rubrics\` is removed from Paths` over `const _rubrics: string = paths.rubrics;`). The file's own comment (lines 67-69) states the mechanism: each directive is "used" only because the field is not declared. The project compiles under `strict: true` (`tsconfig.json`), and the `typecheck` gate is `tsc --noEmit` (`package.json` line 31). The instant Task 1 makes `rubrics` a declared optional field, both index accesses become legal typed access, so the two `@ts-expect-error` directives are now unused and `tsc` fails them with `TS2578: Unused '@ts-expect-error' directive`. I verified this empirically: a minimal `strict` project with an optional field whose `@ts-expect-error` access is now valid reports `error TS2578: Unused '@ts-expect-error' directive`, and the current worktree's `npm run typecheck` exits 0 today (the directives are currently used), so adding the fields is exactly what flips it red.

Task 2 — a separate task (`Depends on: Task 1`), hence a separate commit — is the fix: it removes those two directives, and its own acceptance (line 84) states `tsc --noEmit` passes only *after* the removal. So between the Task 1 commit and the Task 2 commit, the `typecheck` fixed gate cannot be made green. This is the identical green-gate-invariant defect the iteration-1 rejection raised for `npm test` (and which Task 4 now correctly folds in for the smoke fixture): the plan's own Overview commits to "the fixed gate is never red between" commits, but Tasks 1 and 2 violate that for `typecheck`. Task 1's acceptance (lines 67-70) says nothing about `typecheck` staying green, so the red gate is invisible to its per-task acceptance, and every `tdd` task runs the full fixed-gate set after committing.

**Where in plan:** Task 1 (`Files to change: src/config/types.ts`), Task 2 (`Files to change: src/__tests__/core-types.test.ts`), and the ordering Task 1 → Task 2. Anchored to `src/__tests__/core-types.test.ts:76` and `:95`, `tsconfig.json` (`strict: true`), `package.json:31` (`typecheck` = `tsc --noEmit`).

**Suggestion:** Mirror the resolution already applied to the smoke fixture in Task 4. Either (a) fold the `core-types.test.ts` `@ts-expect-error` removal (Task 2's `rubrics` changes) into Task 1 so the type fields and the directive removal land in one commit — add `src/__tests__/core-types.test.ts` to Task 1's `Files to change` and a "`npm run typecheck` stays green at this commit" line to Task 1's acceptance; or (b) reorder so the `core-types` flip is the very next commit after Task 1 and add an explicit acceptance line to whichever task first declares `rubrics` asserting `tsc --noEmit` passes at that commit. Option (a) matches how Task 4 already handles the structurally identical smoke-fixture case. (Note: only the two `rubrics` directives need to move together with the type change; the `description`/`prompt`/`acceptance` directives are unaffected and can stay in a later test-only edit.)

**Why it matters:** The plan lists `npm run typecheck` as a fixed gate every `tdd` task must satisfy on the shared branch, and it adopts "the fixed gate is never red between commits" as an explicit invariant (Overview; the entire rationale for folding the smoke-fixture flip into Task 4). Leaving `typecheck` red across the Task 1 → Task 2 boundary means the Task 1 commit cannot be individually verified or safely committed, reintroducing — for a different gate — exactly the per-task green-gate violation iteration 1 rejected.
