# Design Doc Review

## Verdict: rejected

## Summary

This is a high-quality design: the mechanism claims (judge prompt assembly order, rubric lead-in and activation-key semantics, `# Skills` strip, hook-owned plugin activation, conformance-test inventory, e2e-removal banned strings, changeset-gate patterns) were all independently re-verified against branch code and hold; the trunk coverage survey's per-scenario facts (bullet counts, e2e test counts, observable-assertion paraphrases, the double-embed and 5-extra-posts fixture deltas, the derived-double skill attribution as the single instance, the async-fetch stub URL and request-count assertion) were re-derived from `origin/trunk` and match; the workspace decision (R7/AC6) is recorded with a real, evidence-backed rationale and a concrete future shape, and the PR #5 precedent (commit `6ac4044`) is real. However, the doc contradicts its own coverage survey on the total bullet count, and its handling of config-fetch's live nonce-header assertion is non-deterministic in a way that can silently violate AC2/R4 — exactly the coverage-parity promise this revision exists to restore. One additional wording ambiguity in the fixed decision-rule opener risks non-trunk-faithful verdict semantics. All three are cheaply fixable; the architecture itself needs no rework.

## Issues

### Issue 1: "All 55 acceptance bullets" contradicts the design's own survey table, which sums to 63

**What's wrong:** The survey table's per-scenario bullet counts (5, 8, 4, 5, 9, 6, 5, 3, 7, 6, 5) are each correct — I re-counted every trunk `scenario.yaml` — but they sum to **63**, not 55. The sentence immediately below the table says "All 55 acceptance bullets across the 11 scenarios are check-shaped (none narrative); none is behavior-only." The research record carries the same error (its Topic 2 inventory separately estimates "~55 scenario-common lines" across the current briefs — the two 55s appear to have cross-contaminated).
**Where in design doc:** "Trunk coverage shape (design-phase evidence, not a transcription source)", the paragraph after the table (design-doc.md line 60); mirrored in design-doc-research.md ("Shape survey" preamble).
**Suggestion:** Change 55 → 63 in both files, and re-confirm the "all check-shaped / none behavior-only" claim was actually evaluated over all 63 bullets rather than 55 of them (my spot-reads of the six largest scenarios support the claim, but the doc should assert it against the correct total).
**Why it matters:** The entire design rides on exact coverage parity, and this table is the evidence reviewers are told to orient by. An arithmetic contradiction inside the coverage survey undermines the doc's R10 verification posture and will confuse the code-phase reviewers who use the total as a parity cross-check.

### Issue 2: config-fetch's live `X-WP-Nonce` assertion is handled non-deterministically — "may instruct" instead of rule 5's mandatory conditional

**What's wrong:** Trunk's config-fetch `e2e.spec.mjs` observably asserts that the click-triggered request carries a **non-empty `X-WP-Nonce` header** (`capturedNonce` truthy and not `'undefined'`) — the design's own survey table lists it as coverage, and it is also trunk acceptance bullet 4 (an R4 both-modes overlap). Decision 4 rule 5 correctly mandates an explicit conditional fallback for unperformable live assertions, but names async-fetch as "the exception" and then treats config-fetch's header check as optional: "the live bullet **may** instruct inspecting the request's headers if the tooling exposes them" — while the Risks section admits header observability via `browser_network_requests` is **unverified**. Two implementers following this design produce different briefs: one with a live header bullet, one with the header silently absent from `## Behavior checks` and no fallback conditional. The latter violates AC2 ("every behavior that spec asserted is present as a live behavior check") and R4. Note the gap is not implicitly covered by the other live bullets: a successful live title render does **not** prove the nonce was sent (a GET to `/wp/v2/posts/1` on a public post succeeds without any nonce), so the header assertion is genuinely additional live coverage.
**Where in design doc:** Decision 4, rule 5 (the config-fetch sentence); echoed in Risks and Open Questions ("whether config-fetch's live bullet mentions optional header inspection").
**Suggestion:** Bring the header assertion under rule 5's explicit-conditional pattern instead of leaving it optional: the config-fetch brief's behavior section must carry the header observation as a live check, with an explicit conditional fallback to code-check bullet 4 when the browser tooling does not expose request headers (mirroring the async-fetch treatment). Alternatively, verify header observability in the judge environment during the code phase and mandate the bullet unconditionally — but the design must pick one deterministic rule, not "may".
**Why it matters:** This is the one place the design permits a trunk-asserted observable behavior to drop out of the behavior section with no recorded degradation rule. That is precisely the silent-coverage-loss failure mode this whole revision exists to fix (the counter brief lost its checks the same way — by conversion-time discretion).

### Issue 3: The fixed opener's "every check" leaves the rubric outside the all-must-pass fold

**What's wrong:** Decision 3 fixes the opener verbatim: "Judge the produced work against the checks below … Pass only if every check is satisfied." On trunk, `classifyVerdict` failed the pair when **any rubric item** failed, not just acceptance items — I verified this in `origin/trunk:src/reports/verdict.ts` (both the `rubrics` map and the `acceptance` array feed the fold). In the template, the rubric instruction is a prose sentence after the code-check bullets ("Also check the produced code against the … rubric"), not obviously one of "the checks below" — a judge can defensibly read "every check" as the bulleted checks only and pass work that violates the rubric. Since the design's stated purpose for the opener is restoring trunk's mechanical all-must-pass strictness, and the design freezes the opener wording itself (only the test fragment is deferred to the code phase), this ambiguity is a design-level gap, not a code-phase detail.
**Where in design doc:** Decision 3, "Opening line (decision rule)" and the fixed rubric sentence; the worked counter example.
**Suggestion:** Adjust the fixed wording so the rubric is unambiguously inside the fold — e.g. "Pass only if every check below, including the rubric check, is satisfied", or phrase the rubric sentence as a check ("As an additional code check, verify the produced code against the … rubric"). Keep the eventual conformance-test fragment (Decision 5, assertion 6) consistent with whatever wording is chosen.
**Why it matters:** Trunk-faithful verdict semantics is the design's own justification for adding the opener (and it pre-flags the opener for reviewers as "verdict semantics, not coverage"). If the rubric can escape the all-must-pass rule, the restored decision rule is strictly weaker than trunk's, and the R2 rubric check becomes advisory in practice.
