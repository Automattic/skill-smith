## Issues

### Issue 1: The "exactly 12 files" diff-surface assertion false-positives once any `.pipelines/` artifact commits into the range

**What's wrong:** Task 13's acceptance and Flows 5–7 define the revision diff as `git diff <parent-of-Task-1's-commit>..HEAD` and require it to list **exactly 12 files**. But `.pipelines/**` is git-tracked on this branch (177 files today), and pipeline agents commit artifacts to it mid-phase. The branch's own history proves the failure mode: commit `3f446b4` ("Reject code review") is a code-review rejection artifact committed between code-writer task commits, followed by fix commits. If this run's code phase has even one code-review rejection, the rejection file (`.pipelines/…/4-code/code-review-1-rejected.md`) lands inside the range, the diff lists 13+ files, and Task 13's acceptance criterion — and Flow 5's "exactly 12 files" expectation — can never again be satisfied as written, even though nothing is actually wrong with the code surface. The same brittleness applies if the docs plan or any other artifact is committed after Task 1's commit (in the review-2 run the docs plan happened to land before the first code task; nothing guarantees that ordering here).

**Where in plan:** Task 13, Acceptance bullet 4; E2E test plan preamble ("Revision diff" definition); Flows 5, 6, and 7.

**Suggestion:** Scope the diff to the surfaces the assertion actually cares about, e.g. `git diff <parent-of-Task-1's-commit> HEAD --stat -- ':(exclude).pipelines'` (or equivalently restrict to `src/ testing-project/` plus an explicit "nothing outside these paths changed except `.pipelines/**`" clause). Apply the same fix in the "Revision diff" definition so Flows 5–7 inherit it.

**Why it matters:** A rejection cycle is a normal, designed-for pipeline event — the plan's own guardrail acceptance must survive it. As written, the first code-review rejection permanently wedges Task 13's acceptance: the code-writer fixing any task can no longer demonstrate the criterion, and the reviewer re-running Flow 5 gets a spurious failure that looks like scope creep but isn't. The review then either stalls on a phantom issue or starts waiving acceptance criteria ad hoc — exactly what a plan is supposed to prevent.

### Issue 2: The config-fetch setup bullet leaves the post-ID-1-absent case unhandled, only partially discharging the design's wp-env-content risk

**What's wrong:** The design doc (Risks: "wp-env default content assumption (config-fetch)") is explicit that the behavior check "must not silently depend" on post ID 1 existing, and names exactly two acceptable discharges: "the code phase verifies once against the real warm env, **or** words the check to tolerate confirming/creating the target post via the WP-CLI bridge." Task 4 handles only the *title* half of the risk (no hard-coded "Hello world!" — the lookup bullet is good for that) but neither schedules the one-time warm-env verification nor gives the setup bullet an absence path. `Setup: using the WP-CLI bridge, look up the post with ID 1 and note its title — that is the text the block must render.` says nothing about what the judge does when the lookup returns nothing — and "creating" post ID 1 after the fact is not generally possible (`wp post create` auto-assigns IDs), so the wording can't be trivially patched at judge time either. If post 1 is absent in the judge env, bullets 2–4 of the live sequence fail against the produced block through no fault of the code under test.

**Where in plan:** Task 4, Changes (the four-bullet Behavior checks spec, first bullet); Task 4 Traces to (cites the design risk but doesn't fully execute it).

**Suggestion:** Pick one of the design's two options and make it explicit in Task 4. Either (a) add a step/acceptance item instructing the code-writer to verify once against the real warm judge env (via the wp-env hooks or the bridge) that post ID 1 exists — recording the result in the task's commit message or the bullet's final wording — or (b) extend the setup bullet's normative wording with an explicit absence clause (e.g. "if no post with ID 1 exists, this is an environment fault, not a block failure — report it in the notes rather than failing the block", or equivalent wording of the plan's choosing that keeps the check deterministic). Option (a) is the smaller change and matches the design's first-listed mitigation.

**Why it matters:** The design doc is binding, and it delegated this exact risk to this phase by name. As written, two code-writers would both transcribe a setup bullet whose failure mode misgrades the block on an environment defect — the precise "silent dependence" the design forbade. It also undermines Flow 2's promise that conditional/degradation behavior is "never silently absent": the nonce bullet got the mandatory-conditional treatment, but the post-existence dependence in the very same brief did not.
