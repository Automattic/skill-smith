# Design Doc Review

## Verdict: rejected

## Summary

This is a well-researched design whose hard claims survive adversarial verification: the fs-tools `resolveInside` jail is real (`src/providers/lib/fs-tools.ts:47-55` rejects `..`/absolute paths, and judges on API providers get exactly `{ Read }`), so the inside-cwd placement amendment over the reviewer's sibling is correct; the per-pair copy reasoning holds (default judge concurrency is `parallel`, write-capable judges exist, nested scenario ids exist); the cleanup verdicts check out against the code (the `feature-changeset.test.ts` "exactly one feature changeset" assertion is genuinely tripped by this revision's own mandated changesets; the `enumerate-rubrics.test.ts` opaqueness tests are live contracts, correctly kept-with-reframe; `runWpCli` pins `cwd: PROJECT_ROOT` while the bridge inherits caller cwd and `resolve-cwd.ts` allows a parent-dir harness cwd, so the collapse rejection is sound; `env:start`/`env:stop` have zero consumers after findings 1 and 5); the disposition table covers all 12 proposals plus `dirName` with exactly one disposition each and no prior-art rejections; the conformance-test plan matches the actual invariants in `testing-project-scenarios.test.ts` and the tightened path-form assertion cannot silently pass on a stale bare-id brief; and the changeset plan matches `.changeset/config.json`'s `changedFilePatterns`, the pre-1.0 policy, and the verified-stale prose of `flexible-scenarios-judge-verification.md`. However, the design omits a component that its own breaking type changes force through the AC8 typecheck gate (`examples/skillsmith.config.ts`), leaves an uncovered silent-failure path in the R3/AC4 missing-item guarantee (the failure duty is emitted only when a library is configured), and underspecifies two contracts of the new mechanism (inline-fallback disk behavior; `judging` block presence) enough that two implementers would diverge. Rejected to close those before planning.

## Issues

### Issue 1: `examples/skillsmith.config.ts` is missing from the change inventory, and it gates AC8's typecheck

**What's wrong:** The root `tsconfig.json` includes `examples/**/*`, and `npm run typecheck` is `tsc --noEmit`. `examples/skillsmith.config.ts` sets both removed surfaces: `prompt: judgePrompt` on the judge role (line 167, fed by `readFileSync` boilerplate) and `paths: { rubrics: './eval/rubrics' }` (line 201). The moment `src/config/types.ts` drops `Paths.rubrics` and splits the judge input type to `{ agent, library?, concurrency? }`, the example config fails `tsc` — so it must change in the code phase, in the same change as the type removal, or the AC8 gate goes red. The design's Components → Modified list names `src/index.ts`, the testing-project, and the test blast radius, but not `examples/skillsmith.config.ts`; the doc's only treatment of examples is via R8/phase-5 docs realignment, which runs after the code phase. The research doc even recorded the fact ("Typecheck catches removal only in examples/ (root tsconfig)") — it was dropped on the way into the design doc.
**Where in design doc:** Components → Modified; "Changeset plan" baseline facts; Risks (absent from all).
**Suggestion:** Add `examples/skillsmith.config.ts` to the Modified components with the minimum code-phase edit (swap the judge `prompt` + `readFileSync` boilerplate and the `rubrics` key for the `library` form; the fuller prose/comment realignment can stay phase-5), and note the ordering constraint so the planner co-schedules it with the type removal. While there, state whether the example's comment blocks count as consumer docs (phase 5) vs compile-blocking code (phase 4) so the split is explicit.
**Why it matters:** An implementer or planner working from the component list as written produces a code phase that fails `npm run typecheck` (AC8), and the "fix" would be invented ad hoc outside the design.

### Issue 2: The missing-item failure duty vanishes exactly when the library is unconfigured — a silent-failure path R3 forbids

**What's wrong:** R3's clause is unqualified: "A brief's reference to a missing item must fail observably (in the verdict notes or earlier), never silently" (AC4 restates it). The design's three layers don't cover one case: layer 1 (`checkPaths`) fires only when `roles.judge.library` is set; layer 2 covers stale removed keys; layer 3 — the only layer that actually handles "brief names a missing item" — is the selection-and-failure instruction inside the `# Judge library` section, which the design emits "only when `roles.judge.library` is configured". So a brief that references `judge-library/rubrics/….md` while no library is configured (the user removed the key but not the brief sentences, or copied the bundled briefs into a fresh project) gets no manifest, no failure instruction, and a judge that merely encounters a read error with no duty to fail — the same silent-deselection failure mode the design elsewhere celebrates fixing. Because migration mistakes are precisely half-done by nature, this is the likeliest real-world missing-item case, not a corner.
**Where in design doc:** "Decision: Observable failure for missing items is layered, earliest-first"; Interfaces → Judge system prompt (section 4's "present only when configured" condition); Failure Modes table (row 3 presumes the instruction exists).
**Suggestion:** Either make the failure duty unconditional — it is verdict semantics like the decision rule, so one sentence in the always-present output instruction ("if the brief references grading material that is not supplied or not readable, fail and name it in `notes`") costs nothing and covers the unconfigured case — or explicitly bound the guarantee in the design ("missing item presupposes a configured library") with the reasoning recorded, so the decision is traceable rather than an accident of section conditionality. The first option looks strictly better and is consistent with the doc's own "harness contract, not project content" argument for the decision rule's home.
**Why it matters:** AC4's "given the named item is missing, then the failure is observable, not silent" has an uncovered instance, and it is the instance a migrating user is most likely to hit.

### Issue 3: The inline-fallback mode's disk-side contract is unspecified

**What's wrong:** For tool-less judges the design replaces the manifest with inlined file bodies, but never says what happens on disk: is the library still copied to `judge-workspace/judge-library/`? Does the collision guard still run? The data-flow section's "hooks see both directories" and the Failure Modes rows ("copy-time collision guard", "copy throws inside the judge bracket") are all written for mounted mode; `prepareJudgeLibrary`'s `mode: 'mounted' | 'inline'` return type acknowledges the split without resolving it. Two implementers reasonably diverge: one copies-and-guards in both modes (hooks see the library; collisions fail even for tool-less judges), the other skips the copy in inline mode (cheaper; hooks see nothing; collisions never fire). Relatedly, the selection-and-failure instruction is phrased against "the manifest" ("missing from the manifest or unreadable") — in inline mode there is no manifest, so the instruction's semantics (not just wording) need a stated inline-mode equivalent.
**Where in design doc:** "Decision: Tool-less degradation rule"; Interfaces → `prepareJudgeLibrary` and Judge system prompt 4(c); Data flow; Failure Modes table.
**Suggestion:** Pin it in one sentence each: whether the per-pair copy and collision guard run in inline mode (recommend yes, for hook parity and uniform failure semantics — the copy is cheap and the guard's determinism shouldn't depend on the judge's tool list), and that the failure duty in inline mode applies to the supplied inlined set.
**Why it matters:** This is the core new mechanism; the "two implementers, same design" test currently fails for its degraded mode, and the Failure Modes table silently stops being true for one provider-configuration class.

### Issue 4: `judging` block presence semantics are unspecified on the non-happy paths

**What's wrong:** The per-pair report sketch shows `{ testing, judging, review }` with only `tokenUsage` marked optional. But `writeAgentReport` runs on three paths today: testing failed (judge never runs — no duration exists), judge dispatch threw (duration exists, usage doesn't, review is `{ skipped }`), and the normal path. The design doesn't say whether `judging` is omitted, present-with-partial-fields, or zeroed on the first two. The changeset and phase-5 docs will describe this schema, and CONTRIBUTING's bump table treats `report.json` field semantics as release surface — so the ambiguity propagates into public contract text.
**Where in design doc:** Interfaces → Per-pair report; "Decision: `judging: { duration, tokenUsage? }` report block"; Components → `agent-loop.ts`.
**Suggestion:** One sentence: `judging` is present iff the judge phase ran (mirroring how `review` degrades to `{ skipped }` when it didn't), with `tokenUsage` present iff the provider reported usage — or whatever rule the design prefers, stated.
**Why it matters:** Additive schema with unstated presence rules is exactly how "optional field" drifts into "sometimes-lying field"; the changeset (action 3) can't be written accurately without this.

### Issue 5: Two supporting claims are inaccurate as written

**What's wrong:** (a) Interfaces → `prepareJudgeLibrary` says "`judge-agent.ts` remains a pure string assembler with no filesystem access of its own." False: `buildUserMessage` in `judge-agent.ts` reads file bodies from the judge workspace via `readFileSync` (judge-agent.ts:312-331) and survives this design (finding 13 only parameterizes the shared inlining helper). The purity claim holds for the system-prompt path only; as written it invites an implementer to relocate the user-message inlining — an unplanned, behavior-relevant refactor. (b) Risks says "codex never triggers it (its sandbox always reads)" about the tool-less predicate. The predicate as defined ("`capabilities.tools` is an explicit array containing neither `Read` nor `Bash`") triggers for a codex judge configured with, e.g., `tools: []` — `judgeCapabilities` sets `capabilities.tools` whenever the agent definition carries an array, provider-independent. The direction is harmless (inlining while the sandbox can also read), but the sentence contradicts the predicate's own definition two sections earlier.
**Where in design doc:** Interfaces → `prepareJudgeLibrary` (division-of-labor paragraph); Risks → "The tool-less heuristic is provider-vocabulary-coupled".
**Suggestion:** (a) Scope the claim: "judge-agent performs no filesystem access for system-prompt assembly; the user-message file inlining stays where it is." (b) Correct to: "codex judges without an explicit `tools` array never trigger it; an explicit non-Read/Bash array triggers harmless inlining alongside a sandbox that can still read."
**Why it matters:** Both sentences are load-bearing for implementers deciding what to move and what to test; small inaccuracies in a doc this precise get trusted and propagated.
