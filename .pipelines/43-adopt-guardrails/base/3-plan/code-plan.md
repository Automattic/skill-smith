# Code plan — Adopt Radical Pipelines guardrails (#43)

## Orientation

This is a **documentation-and-configuration** change. There are no new runtime
modules and no `src/` edits. The net artifacts (design doc §8) are:

1. `testing-project/package.json` — rename the dependency key
   `skillsmith` → `@automattic/skillsmith`, and add a `check:config` script.
2. `testing-project/package-lock.json` — refreshed by `npm install` in
   `testing-project/` (re-keys the dependency and absorbs pre-existing drift).
3. `testing-project/eval/utils/verify-e2e.ts` — optional, recommended: align the
   line-11 import specifier to `@automattic/skillsmith`.
4. `scripts/bootstrap-worktree.sh` — new, committed, `set -euo pipefail`, two
   `npm ci`s.
5. `.rp.md` — insert `## Worktree bootstrap` (after `## Claude Code worktrees`)
   and append `## Guardrails` (last).

The tasks below are ordered so that the config-smoke enablers (T1) land before
anything that asserts config-smoke is green. Each task is independently
executable by a fresh code-writer and carries its own acceptance checks.

**Verification commands (run from the worktree root unless noted):** dependencies
are already installed in this worktree (root and `testing-project/`), so the
gates run directly. The repo root `package.json` has no `workspaces` key, so the
two npm workspaces are installed independently.

There is no automated unit-test surface for these artifacts (they are config,
shell, and markdown). "TDD where applicable" therefore reduces to **running the
declared guardrail commands themselves as the acceptance check** for each task —
each task states the exact command(s) and the expected exit code. Do not add new
unit tests for these artifacts; the guardrail commands are the tests.

## T1 — config-smoke enablers: dependency-key rename, `check:config` script, lockfile refresh

**Goal.** Make `@automattic/skillsmith` resolvable from `testing-project/` and add
the `check:config` script, so that `npm --prefix testing-project run check:config`
(the config-smoke gate) exits 0 on trunk. (R3, R4)

**Files.**
- `testing-project/package.json` (edit)
- `testing-project/package-lock.json` (regenerated by `npm install`)

**Changes.**

1. In `testing-project/package.json`, rename the dependency key under
   `"dependencies"`:
   ```diff
   -    "skillsmith": "file:.."
   +    "@automattic/skillsmith": "file:.."
   ```
   The repo root package `name` is `@automattic/skillsmith`, so after the rename
   `npm install` links `node_modules/@automattic/skillsmith` → the repo root and
   the config's `import … from "@automattic/skillsmith"`
   (`testing-project/skillsmith.config.ts:4`) resolves at runtime.

2. In `testing-project/package.json`, add this script to the `"scripts"` block
   (byte-for-byte, including the escaped quotes):
   ```json
   "check:config": "node --import tsx -e \"await import('./skillsmith.config.ts')\""
   ```
   This imports the config and its full module graph — nothing more. It spawns no
   agent, boots no wp-env, needs no API key, and makes no network call.
   (`defineConfig` at `src/config/define-config.ts` is a pure identity
   passthrough; validation/normalization happens only later at load time, which
   this script never invokes.) Match the file's existing tab indentation and JSON
   style.

3. Refresh the lockfile by running, from the worktree root:
   ```
   npm install --prefix testing-project
   ```
   This re-keys the dependency to `@automattic/skillsmith` and replaces the bare
   `node_modules/skillsmith` symlink with the scoped one. **Expect a lockfile
   diff larger than the dependency-key rename alone**: `testing-project/package-lock.json`
   is already stale relative to the current root `package.json` (it records the
   old mirrored `zod` version and is missing the `@changesets/*` devDeps and the
   root `name` field), and this `npm install` absorbs that pre-existing drift in
   the same update. This is expected, not scope creep (design doc §5.1). Use
   `npm install` here (the one-time R3 lockfile re-key), **not** `npm ci` — `npm ci`
   will not re-key the dependency. (`npm ci` is reserved for the per-run bootstrap
   in T3; do not conflate the two.)

**Depends on.** Nothing.

**Traces to.** R3, R4; AC1 (config-smoke resolves to a runnable script), AC2
(config-smoke reaches exit 0 after this task).

**Acceptance.**
- `testing-project/package.json` has the dependency key `"@automattic/skillsmith": "file:.."`
  (and no longer `"skillsmith": "file:.."`), and a `"check:config"` script whose
  value is byte-identical to the string above.
- `testing-project/package-lock.json` is updated (it now keys the dependency under
  `@automattic/skillsmith` and links the scoped symlink).
- From the worktree root, **`npm --prefix testing-project run check:config`
  exits 0** (this is the config-smoke gate, green on trunk now that the
  prerequisites are applied).
- From the worktree root, **`npm run typecheck` still exits 0** — the rename does
  not regress typecheck (root `tsconfig.json` does not compile `testing-project/`,
  so the bare type-only import at `verify-e2e.ts:11` is never type-checked by this
  gate; design doc §5.1).

## T3 — Add the worktree-bootstrap helper script

**Goal.** Provide the committed body that performs a complete, clean install of
both npm workspaces, so a fresh worktree is fully installed before any gate runs.
(R5)

**Files.**
- `scripts/bootstrap-worktree.sh` (new)

**Changes.**

Create `scripts/bootstrap-worktree.sh` with exactly this content:
```bash
#!/usr/bin/env bash
set -euo pipefail

npm ci
npm ci --prefix testing-project
```

Then make it executable:
```
chmod +x scripts/bootstrap-worktree.sh
```

Rationale captured for the writer (design doc §6): **two `npm ci` commands are
genuinely required, not belt-and-suspenders** — the root `package.json` has no
`workspaces` key, so a single root `npm ci` does not install `testing-project/`;
the two workspaces have independent lockfiles and each must be installed on its
own. Both lockfiles are `lockfileVersion: 3`, so `npm ci` is valid in both.
`npm ci` (not `npm install`) is mandated by R5's "complete, clean install"
definition: it wipes `node_modules` and installs exactly the lockfile,
eliminating the partial-tree failure mode that makes `npx` gates nondeterministic.
`set -euo pipefail` makes a partial or failed install a non-zero exit, so a broken
bootstrap surfaces loudly. The `scripts/` directory already exists
(`scripts/validate-changesets.ts`), so this adds no new structure.

**Depends on.** Nothing. (T5 will *name* this script in `.rp.md`; the script must
exist for that reference to resolve, but the two tasks may be done in either order
as long as both land in the PR.)

**Traces to.** R5; AC5 (the bootstrap that precedes gates).

**Acceptance.**
- `scripts/bootstrap-worktree.sh` exists, is executable (`test -x
  scripts/bootstrap-worktree.sh`), starts with the `#!/usr/bin/env bash` shebang,
  and contains `set -euo pipefail` followed by `npm ci` and
  `npm ci --prefix testing-project` (in that order).
- `bash -n scripts/bootstrap-worktree.sh` exits 0 (valid bash syntax). **Do not
  execute the script in this worktree** — running `npm ci` would wipe and reinstall
  both `node_modules` trees, which is unnecessary here (deps are already installed)
  and slow; syntax-checking is sufficient to validate the artifact.
- From the worktree root, **`npm run lint` exits 0** (lint must still pass; a
  `.sh` file is outside biome's TS/JS scope but confirm nothing regressed).

## T4 — Append the `## Guardrails` section to `.rp.md`

**Goal.** Declare the six guardrails as a committed table with accurate per-gate
prose, as the final top-level section of `.rp.md`. (R1, R2, R6)

**Files.**
- `.rp.md` (edit — append at end)

**Changes.**

Append a new top-level `## Guardrails` section as the **last** section of
`.rp.md`, immediately after `## Health monitoring` (currently the file's last
section, ending at line 81). It is a **peer `##`**, not a `###` nested under a
grouping heading — this repo's `.rp.md` is a flat, one-`##`-per-convention file
with no `## Shared conventions` wrapper, so a peer `##` matches the file's shape
(design doc §4.2, D1). It must be committed to `.rp.md`, never to `.rp.local.md`
(the plugin reads Guardrails only from the committed file).

The section must contain, in order:

1. A one-line description of what the gates are (exit-code-only verification
   commands the pipeline runs at the named phase(s), each judged pass/fail solely
   by exit code, run from the repo root).
2. The exact six-row table below, header `| Name | Command | Phase |`
   (commands and phase values are load-bearing and must be byte-for-byte; the
   Name column is a human label only):

   | Name             | Command                                          | Phase      |
   | ---------------- | ------------------------------------------------ | ---------- |
   | typecheck        | `npm run typecheck`                              | code       |
   | lint             | `npm run lint`                                   | code       |
   | tests            | `npm test`                                       | code       |
   | config-smoke     | `npm --prefix testing-project run check:config`  | code       |
   | changeset-format | `npx tsx scripts/validate-changesets.ts`         | code, docs |
   | changeset-status | `npx changeset status --since=origin/trunk`      | docs       |

3. Accurate prose about the two changeset gates that **does not over-claim**
   (R6, design doc §4.3, D3). The prose must convey:
   - **changeset-format** (`code, docs`) validates the *shape* of every
     `.changeset/*.md` that exists (front-matter fence, valid bump type, known
     package name, non-empty body, pre-1.0 `major` forbidden) and is
     **presence-agnostic** — it passes when no changesets exist and never asserts
     a changeset is present. That presence-agnosticism is exactly why it is safe
     on both phases, including the code phase where no changeset has been authored
     yet.
   - **changeset-status** (`docs`) is a **conditional changeset-presence check**:
     it exits non-zero **if and only if** the branch changed a *versionable* path
     **and** no `.changeset/*.md` file exists. "Versionable" is the set matching
     `.changeset/config.json` `changedFilePatterns`: `src/**`, `bin/**`,
     `package.json`, `examples/**`, `README.md`, excluding `src/__tests__/**`. The
     intended guarantee is the **conditional** one — "release-relevant
     (versionable) changes carry a changeset" — and the prose **must not** imply
     "the doc-writer always authors a changeset regardless of what changed." A
     docs-phase change confined to non-versionable paths (e.g. `AGENTS.md`,
     `CONTRIBUTING.md`, `.rp.md`, `.pipelines/**`) is correctly **not** forced to
     carry a changeset.
   - Two empirically-verified properties worth stating so they don't create false
     expectations: (a) **an empty changeset counts as "present"** — the gate keys
     off whether a `.changeset/*.md` file exists, not whether it bumps a package,
     so an empty (`---\n---\n`) or `none`-bump changeset satisfies it, matching the
     project's documented "empty changeset" escape; (b) the gate **has real teeth,
     including for `README.md`** — a versionable-path change with no changeset
     exits non-zero, while the `!src/__tests__/**` exclusion lets test-only changes
     pass.
   - Optionally, a one-line continuity note (rationale, not new policy): these two
     gates are a one-to-one lift of the repo's existing GitHub Actions changeset
     gate (`.github/workflows/changeset-gate.yml`), so adopting them as Guardrails
     is continuity, not a new contract.

   Match the surrounding `.rp.md` house style (prose tone, list style). The exact
   wording is the writer's; the **commands, phase values, and the no-over-claiming
   constraints above are load-bearing**.

The `--since=origin/trunk` form of `changeset-status` is deliberate (it compares
against the remote-tracking ref, safe in a pipeline worktree where local `trunk`
may be stale or absent) — do not change it to `--since=trunk`.

**Depends on.** Nothing for the text itself. (The config-smoke command it names
becomes green via T1; the table is just declaration text and can be written
independently. T5 also edits `.rp.md` — see the note in T5 on coordinating the two
`.rp.md` edits.)

**Traces to.** R1, R2, R6; AC1 (each declared command resolves), AC4 (the
changeset prose matches the gates' actual behavior).

**Acceptance.**
- `.rp.md` ends with a top-level `## Guardrails` section (peer `##`, appended
  after `## Health monitoring`).
- The section contains the six-row table with header `| Name | Command | Phase |`,
  and the Command and Phase cells are byte-for-byte the six rows above (verify
  each command string and each phase value, especially `code, docs` for
  changeset-format, `docs` for changeset-status, and `--since=origin/trunk`).
- The changeset prose states the conditional guarantee for changeset-status and
  the presence-agnostic/shape-only guarantee for changeset-format, and does **not**
  claim changeset-status forces a changeset for every docs-phase change.
- From the worktree root, **`npx tsx scripts/validate-changesets.ts` exits 0**
  (changeset-format on this branch) and **`npx changeset status
  --since=origin/trunk` exits 0** (this branch's changes so far are confined to
  non-versionable paths — `.rp.md`, `scripts/`, `testing-project/` — so no
  changeset is required; if a versionable path was touched, this would correctly
  require one).

- Explains (briefly) that the script performs a complete, clean install of **both**
