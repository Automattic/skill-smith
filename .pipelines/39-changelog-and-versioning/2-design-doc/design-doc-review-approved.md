# Design Doc Review

## Verdict: approved

## Summary

Iteration 3 resolves the three blockers from iteration 2 with empirical verification that holds up under independent re-checking. The bootstrap routine is now structurally safe: it never disables the workflow (Issue 1 retired), the `none`-bump starter survives `changesets/action` v1.4.0+'s empty-only early-return (Issue 2 resolved with an inline empirical reproduction matching the action's `src/index.ts` switch), and the `skip_publish` kill switch uses the inverted ternary form that actually fires (Issue 3 resolved). Two new open questions (OQ-6 and OQ-7) surface spec-vs-design gaps that the design clearly flags rather than papers over. The design is internally consistent, traces every Decision to one or more spec items, considers credible alternatives for each load-bearing choice, and surfaces residual risks with concrete recovery paths. Approving for the plan phase.

## Iteration-2 blockers — verified resolved

For the orchestrator's confidence I empirically re-verified each fix:

- **Iteration-2 Issue 1 (disable + `workflow_dispatch` is mutually exclusive).** RESOLVED. The design no longer asks the maintainer to disable the workflow at any point. `release.yml` ships with `on: workflow_dispatch:` as its **only** trigger; the workflow stays enabled throughout the bootstrap, so the "Run workflow" UI works and the manual run #1 succeeds. The push trigger is added by the follow-up D4 feature PR alongside the first real changeset. Decision: "Bootstrap via `workflow_dispatch`-only trigger" (design-doc.md:885) and the rewritten "Empty-changeset mechanics for the first release" section (design-doc.md:625–806) document this end-to-end, including six considered alternatives (A–F) and why each non-chosen path is rejected. The flow diagram, components table, release-workflow interface, failure-modes table, risks, and OQ-7 are all updated consistently.

- **Iteration-2 Issue 2 (`changesets/action` v1.4.0+ skips PR creation for empty-only state).** RESOLVED. The starter changeset is now a `none`-bump entry (`---\n"@automattic/skillsmith": none\n---\n\nInitial scaffolding...\n`), not the canonical empty `---\n---\n` form. I empirically re-verified the design's claim against `@changesets/read@0.6.7` (the same library `changesets/action` uses) in `/tmp/changeset-verify-39-fresh`: the canonical empty form yields `{releases: [], summary: ""}` (so `hasNonEmptyChangesets=false`, action returns "All changesets are empty; not creating PR"), while the `none`-bump form yields `{releases: [{name: "@automattic/skillsmith", type: "none"}], summary: "Initial scaffolding."}` (so `hasNonEmptyChangesets=true`, action's fourth switch case fires and `runVersion` runs). I also re-verified that `changeset version` with the `none`-bump entry against the project's exact config produces precisely the D2 diff: deletes the starter file, leaves `package.json:version` at `0.1.0`, and does not create `CHANGELOG.md` (this matched the design's `/tmp/none-bump-test-2` reproduction at design-doc.md:687–703). The validator's R-shape-2 rule still recognizes the canonical empty form as valid for the contributor-facing escape hatch (R1.3, R2.4), so only the starter form changes.

- **Iteration-2 Issue 3 (`skip_publish` ternary trap).** RESOLVED. The YAML expression is now `${{ !inputs.skip_publish && 'npx changeset publish' || '' }}` (the inverted form). I empirically re-verified the truth table at design-doc.md:531–536 in Node 20 against GitHub Actions' truthiness rules: `skip_publish=true` resolves to `''`; `skip_publish=false` or `undefined` resolves to `'npx changeset publish'`. The kill switch now actually fires. The design's "Empirical verification of the `skip_publish` expression" subsection (design-doc.md:519–551) makes the contract testable from the design alone, and the Decision: "`workflow_dispatch` kill switch (`skip_publish`) — ternary-trap-safe expression" (design-doc.md:960) mandates the inverted form explicitly and rejects the naive form with rationale. Iteration 3 also notes (correctly) that under the chosen `workflow_dispatch`-only bootstrap, the kill switch is *defense-in-depth* rather than load-bearing — the structural protection is that this PR ships no `push:` trigger.

## Verdict on OQ-6 and OQ-7

- **OQ-6 (R8.6 / A6 wording vs. action behavior) — acceptable as flagged.** The spec's text ("one empty changeset ... containing `---\n---`") is incompatible with the same spec's pin on `changesets/action@v1.8.0`, whose v1.4.0+ early-return skips opening a Version Packages PR for empty-only state. The design's `none`-bump substitution preserves D2's substantive contract bit-for-bit (delete the starter, no version bump, no `CHANGELOG.md` change — empirically verified inline and re-verified by me at review time) while contradicting the spec's surface wording. The design flags this in OQ-6 with explicit "the orchestrator should surface to the owner" language and proposes concrete revised wording for R8.6 / A6 ("one starter changeset (a `none`-bump or the empty form, see design doc)"). This pattern — substantive intent preserved, surface text revised, gap surfaced — is exactly the right move for a design phase that discovers a spec-internal contradiction. The orchestrator/owner should ratify the substitution and revise R8.6 / A6 wording before code review of the implementation, but design approval does not block on it.

- **OQ-7 (D1 / F1 wording vs. workflow_dispatch-only initial trigger) — acceptable as flagged.** Spec D1 ("Merging this PR to `trunk` triggers `release.yml`") and F1 ("the first `release.yml` run on this PR's merge commit succeeds") presume an automatic-trigger flow. The design's bootstrap routine substitutes a manual `workflow_dispatch` run while preserving the substantive intent (the lint/typecheck/test sequence runs against `trunk`'s state and exposes any regressions; the workflow runs successfully). The substitution is necessary because the alternative — automatic trigger on this PR's merge — would invoke `npm publish` for `@automattic/skillsmith@0.1.0` on the no-op Version Packages PR merge, contradicting D3 (npm has no `0.1.0`; the publish branch's `infoAllow404` check would pass it through to `npm publish`). OQ-7 flags this with explicit proposed wording for D1 and F1. The same logic as OQ-6 applies: the orchestrator/owner ratifies the substitution and revises D1 / F1, but design approval does not block on it.

Both gaps point at spec-internal contradictions (empty starter vs. v1.8.0 pin; auto-trigger D1 vs. no-prior-version publish problem) that surfaced only when the design did the empirical work the spec did not. The design's job is to surface them honestly, which it does in OQ-6 and OQ-7, and to propose corrected wording — which it also does. Resolving the spec text is downstream of approval.

## Caveats and non-blocking notes for the implementer

These do not change the verdict; the implementer can address, defer, or ignore as appropriate.

- **Typo in bootstrap step 6** (design-doc.md:731). The optional smoke-test run #2 narrative reads "The action sees `hasChangesets=false`, `hasPublishScript=true`" and then immediately corrects itself with "the action's `hasPublishScript` check on line 52 evaluates `!!''`, which is `false`". The opener is wrong; the conclusion is right. The implementer should mentally read it as "`hasPublishScript=false`" and proceed. Cosmetic; one-character fix.

- **`R-d4-followup-omits-changeset` is a real residual risk.** If the follow-up D4 PR adds `push: trunk` to `release.yml` but ships without a real changeset, `release.yml` fires on D4's merge, sees zero changesets, and invokes `npx changeset publish` against `package.json:version === "0.1.0"`. With E4 configured, `0.1.0` ships to npm — the very bootstrap failure mode the design is preventing. The design mitigates this only via the PR-description checklist ("UNCOMMENT the `push: trunk` block AND ship a real changeset"). A mechanical guard (e.g., a "fail if no changeset and version starts with 0.1.0" step in `release.yml`) is conceivable but is design-time gold-plating that the spec does not require. Implementer should treat the checklist coupling as load-bearing; the design's risk table at design-doc.md:1075 documents the recovery path if the failure occurs.

- **B1–B8 test assertions should match on `Err.msg` (substring), not on `Err.line`.** Iteration 3 explicitly notes this in OQ-2 ("Test plan implication"). The pseudocode's hard-coded `1` / `2` / `4` line constants are placeholders pending OQ-2 resolution; tests that couple to them will need updating when the implementation uses `yaml`'s source-position API.

- **Validator's R-pkg / R-bump on non-string YAML values.** The pseudocode at design-doc.md:328 casts `parseYaml(fmRaw)` to `Record<string, string>` with an `as`, which is unsound when the YAML value is a number or array (e.g. `"@automattic/skillsmith": 1`). The downstream `VALID.has(bump)` check still catches this correctly because `VALID` only contains strings, but the implementer may want a runtime `typeof bump === "string"` guard for clearer error messages. Not a contract concern.

- **The "uncomment the block" instruction for the D4 follow-up.** The design's `release.yml` interface ships commented-out lines for the `push: trunk` trigger; the D4 PR uncomments them. Implementer should ensure the comment block in the YAML file is unambiguous (e.g., a single contiguous `#` prefix that maps cleanly to a single sed/replace operation), and the D4 PR's review process double-checks that both edits land together.

- **The `validateChangesetFile`'s `Err.file` field stores the bare filename.** Per the test-strategy section (design-doc.md:984), per-rule unit tests assert on the bare filename (`"test.md"`), while the smoke test covers the `.changeset/`-prefixed printed form. Already documented; flagged here so it doesn't surprise the implementer.

- **`tsconfig.json:include` omission for `scripts/**`** (design-doc.md:137). The validator script is type-checked at `tsx` execution time (in CI) and at import time (via the test file's `import`), but not by `npm run typecheck` directly. The design accepts this trade-off; extending `tsconfig.json:include` with `scripts/**/*` is a one-line follow-up if a contributor prefers `tsc` coverage.

- **`actions/checkout@v6` / `actions/setup-node@v6` pins** (design-doc.md:1007). Taken faithfully from the spec; the spec-reviewer surfaced the late-2025 published-major caveat (v4) and the design is faithful to the spec's pin. Implementer should defer to the spec on whether to substitute v4 at code time.

## What was verified

- **Codebase facts.** `package.json` has `yaml@^2.8.3`, `tsx@^4.21.0`, `type: "module"`; `tsconfig.json:include` covers `src/**/*`, `skillsmith.config.ts`, `examples/**/*`. No `.changeset/`, no `.github/`, no `CHANGELOG.md`, no `CONTRIBUTING.md` exist yet. All confirmed.
- **Fence regex behavior.** Verified the design's regex against six canonical inputs (empty with trailing newline, empty without trailing newline, `none`-bump, regular `minor`, CRLF `none`-bump, missing closing fence). All match the design's expected captures or null.
- **`changesets/action` switch logic.** Pulled the action's `src/index.ts` at v1.5.0 and confirmed the switch lines 48–52 (`hasChangesets`, `hasNonEmptyChangesets`, `hasPublishScript`), line 59 (`!hasChangesets && !hasPublishScript`), line 64 (`!hasChangesets && hasPublishScript`), line 114 (`hasChangesets && !hasNonEmptyChangesets`), and line 117 (`case hasChangesets:` → `runVersion` → `return`). Every claim the design makes about the action's switch matches the code.
- **`@changesets/read` behavior.** Installed `@changesets/read@0.6.7` (the latest stable major matching the action's vendored dependency) against a fixture with both the canonical empty form and a `none`-bump entry. Confirmed `releases.length === 0` for empty and `releases.length === 1` for `none`-bump, so `hasNonEmptyChangesets=true` only for the `none`-bump case.
- **`changeset version` behavior on the `none`-bump entry.** Ran `@changesets/cli@^2.31.0`'s `version` command against a fixture with the project's exact config and only a `none`-bump starter. Confirmed: the starter file is deleted, `package.json:version` stays at `0.1.0`, and `CHANGELOG.md` is not created. Matches the design's empirical reproduction at design-doc.md:687–703.
- **Inverted `skip_publish` ternary.** Reproduced the truth table at design-doc.md:531–536. `skip_publish=true → ''`; `skip_publish=false → 'npx changeset publish'`; `skip_publish=undefined → 'npx changeset publish'`. All three rows match.

All load-bearing claims hold up under independent re-verification.

## Conclusion

The design is ready for the plan phase. The implementer should treat OQ-6 and OQ-7 as spec-level concerns the orchestrator/owner will revise; the design's substitutions (none-bump starter, workflow_dispatch-only initial trigger) are the correct mechanical choices given the spec's empirical contradictions, and the substantive D1–D4 / F1–F3 contracts are preserved through the substitutions.
