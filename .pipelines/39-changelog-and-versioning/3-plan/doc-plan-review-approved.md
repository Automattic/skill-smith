# Doc Plan Review

## Verdict: approved

## Summary

The doc plan is thorough, traceable end-to-end, and drift-resistant. Three tasks split the documentation surface cleanly across `CONTRIBUTING.md`, `.changeset/README.md`, and `README.md`, with audience clearly named per task and sequencing that honours the anchor-dependency graph (Task 1 lands `#adding-a-changeset` and `#pre-10-policy`; Tasks 2 and 3 consume them). Every R6 / R7 / R8.5 / R8.7 / R8.8 obligation has a home in a task; R6.2's sub-bullet enumeration is complete; the R3.1 bump-type table is explicitly flagged as load-bearing and must be reproduced verbatim; the two load-bearing anchors are pinned with explicit slug-confirmation acceptance criteria that cross-reference the validator's error string in code-plan Task 6. Coverage of the host project's existing documentation is verified: the existing `README.md` has no install/contrib/changelog sections to conflict with, `docs/index.html` has no install/version references that would drift, and no other repo-root README references the affected behaviour. Scope is well-bounded — no code planning leaks in, no out-of-spec features sneak in, the OQ-5 PR-description checklist is correctly excluded from `CONTRIBUTING.md`, and the bootstrap-only `none`-bump starter distinction is explicitly held out of contributor-facing docs.

- **Drift-resistance.** Acceptance criteria are framed as reader-outcome / coverage requirements ("a first-time contributor can answer X within one section", "the anchor exists and matches the validator's slug", "the R7.2 list appears in the documented order") rather than prose prescriptions. The writer is repeatedly told to read live source-of-truth files (`package.json:name`, `package.json:engines.node`, `package.json:scripts`, the validator's error string) rather than hard-coding values, so a name change at merge time propagates correctly.
- **Audience clarity.** Task 1 names three concrete audiences (first-time contributor, repeat/AI-assisted contributor, maintainer) with each tied to specific sections. Task 2 names contributors who reflexively open `.changeset/`. Task 3 names downstream npm consumers and future contributors. No "general developer" hand-waves.

- **Scope.** Stays within R6 / R7 / R8.5 / R8.7 / R8.8 / A5 / A7 / A8. No bonus content (no code of conduct, no release cadence, no review process). Task 3's acceptance line 155 explicitly forbids out-of-scope additions to `README.md`.

The plan correctly defers those to the PR description.

## Non-blocking nits (observations, not requested changes)

These are observations the doc-writer may find useful in phase 5; they do not block approval.

- **Heading-text-to-slug mapping is implicit.** The plan mandates the anchor `#pre-10-policy` but does not prescribe a heading text. GitHub's auto-slugifier maps "Pre-1.0 policy" → `pre-10-policy` (period stripped, spaces hyphenated), and the writer would have to converge on that or a near variant. The acceptance criterion already requires the writer to verify the slug, so this is self-correcting; an explicit "use the heading 'Pre-1.0 policy'" hint in §4 sub-bullet "Pre-1.0 policy" could shorten the writer's verification loop. Same for `#adding-a-changeset` (heading "Adding a changeset"). Acceptable as-is.
- **External-issue link in §4 "How to add one".** The plan cites `[changesets#346](https://github.com/changesets/changesets/issues/346)` per spec R6.2's reference. If that issue is closed/moved between now and phase 5, the link drifts. The spec itself takes this risk; the plan faithfully inherits it. Acceptable.
- **Worked CHANGELOG.md example placement.** Task 1 §4 puts the worked example as the last sub-bullet of "Adding a changeset". This is per the spec, but a reader-flow argument could put it after the "Bump types" sub-bullet (so the reader sees what the table produces). The doc-writer may exercise judgement here; the acceptance criteria don't pin the ordering of sub-bullets within §4.
