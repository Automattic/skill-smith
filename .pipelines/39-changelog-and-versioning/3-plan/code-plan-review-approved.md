## Caveats

- **Unused `type Err` import in the test file.** Task 6 line 215 instructs the writer to import `type Err` alongside `validateChangesetFile`. None of the listed test cases (B1-B8 + CRLF + CLI smoke) reference `Err` directly — they call `validateChangesetFile` and assert on the returned array. With Biome 2.4.12 and the project's `recommended` lint set, `noUnusedImports` will emit a warning for the unused `type Err`. By default `biome lint` does not exit non-zero on warnings (it requires `--error-on-warnings`), so this does not break `npm run lint`. The implementer has three reasonable resolutions (annotate one assertion with `const errors: Err[] = ...`, drop the `type Err` from the import, or live with the warning); the plan does not pick one. Non-blocking because `npm run lint` will still pass; flagging in case the implementer wants to choose deliberately. The static `import { validateChangesetFile }` alone is already sufficient to pull the script's exported type surface into the typechecker's reachable graph (because `validateChangesetFile`'s return type is `Err[]`), so dropping `type Err` from the import does not weaken the load-bearing typecheck guarantee the plan and design rely on.

- **Action-version caveat permits silent v4 substitution.** Task 7 line 342 and Task 8 line 421 instruct the writer to verify whether `actions/checkout@v6` / `actions/setup-node@v6` are published; if not, substitute `v4` and surface the deviation in the PR description. This is a delegated decision rather than a pinned one. The design explicitly accepts this caveat (design-doc.md line 1008), so it is consistent with the design rather than a hidden plan-level decision. Non-blocking, but worth noting: the writer should commit to either `v6` or `v4` consistently across both files, not mix.

- **Line constants 1/2/4 are now pinned canonical values.** Task 6 line 188 explicitly settles OQ-2 as `1/2/4`, which is stricter than the design's pseudocode-placeholder framing. The test strategy still asserts on `Err.msg` substrings rather than `Err.line` integers (consistent with the design's OQ-2 guidance), so the tests are not coupled to the pinned constants. The pin is fine; it removes one ambiguity for the code-writer without trapping the test suite.

- **`v1.4.0+` vs the plan-cited `v1.5.0` in the design.** The plan's overview (line 14) references "the empty-only early-return at v1.4.0+", which matches the design's "Empty-changeset mechanics for the first release" section. The action pin in both workflows is `@v1` (major-only), so this is internally consistent — the v1.4.0+ behavior is a property of the v1 major the plan and design both target. No action needed.
