# Spec Review

## Verdict: rejected

## Summary

The revision is strong and the three iteration-1 issues are all genuinely resolved. (1) The verify-only check is now pinned to an observable command — Req 7 states the check *is* `biome format .` run without `--write`, declares that no new artifact is required, and the acceptance criteria name the exact commands and their exit-code expectations (`biome format --write .` makes no edits; `biome format .` exits zero on a clean tree and non-zero on a deliberately mis-formatted file). (2) Req 8 now cleanly separates source files (covered by `typecheck`/`test`) from data/generated files, and both Req 5 and Req 8 give an observable lockfile install-equivalence guarantee (`npm ci` resolves and installs with no change to resolved versions), with a matching acceptance criterion. (3) The changeset-gate consequence is now explicitly addressed — there is a dedicated "Changeset mechanics" Out-of-Scope bullet plus an acceptance criterion that the gate passes. I re-verified the spec's premises against the codebase: `biome.json` matches the described baseline, `package.json` confirms the `2.4.12` pin and script names, `testing-project/` and both `docs/` files exist, the `none`-bump changeset precedent exists exactly as cited, `validate-changesets.ts` explicitly accepts `"none"`, and `npm run lint`/`typecheck`/`test` all run in `release.yml`. The rejection is for one remaining moderate gap: the spec deliberately pulls `testing-project/` source files into the reformat surface but provides no observable behavior-preservation guarantee for them, even though a documented check exists for exactly that surface. This is the same gap-class the iteration-1 review rejected for lockfiles — fixed there, but the sibling surface was left uncovered. It needs the same tightening; the spec's direction is otherwise sound.

## Issues

### Issue 1: `testing-project/` source files are reformatted in-scope but have no observable behavior-preservation criterion, despite a documented check existing for exactly that surface

**What's wrong:** Req 5 (line 29) and an acceptance criterion (line 64) deliberately bring `testing-project/` files — including its TypeScript (`testing-project/skillsmith.config.ts`, `testing-project/playwright.config.ts`) — into the reformat surface, and the spec is explicit that "no in-tree exclusions spare them." But the spec's behavior-preservation criteria (lines 74–76) only exercise the *repo's own* source and data:

- `npm run typecheck` runs `tsc --noEmit` against the root `tsconfig.json`, whose `include` is `["src/**/*", "skillsmith.config.ts", "examples/**/*"]` — it does **not** include `testing-project/`.
- `npm test` runs `node --test src/__tests__/*.test.ts` — it does not load `testing-project/` source.
- `npm run lint` is a lint check, not a behavioral one.

So `testing-project/`'s reformatted TypeScript is asserted to be reformatted (line 64) but is covered by *none* of the spec's "behavior preserved" acceptance criteria. Req 8's blanket claim ("never the meaning of the code") logically extends to these files, but the spec pins **no observable check** to them — which is precisely the deficiency the iteration-1 review (Issue 2) called blocking for lockfiles. There the fix was to add an observable guarantee (`npm ci` install-equivalence); the analogous guarantee for `testing-project/` source is simply missing.

Critically, the natural observable check already exists and is documented: `CONTRIBUTING.md:13` lists `npm --prefix testing-project run check:config`, described as loading "the fixture config through its real import graph, catching config-load and import regressions the other checks miss." Its definition (`testing-project/package.json`) is `node --import tsx -e "await import('./skillsmith.config.ts')"` — i.e. it is exactly the check that would catch a reformat that broke `testing-project/skillsmith.config.ts` or its import graph. The spec never references it.

**Where in spec:** Requirement 5 and Requirement 8, and the "Behavior and check preservation" acceptance-criteria block (lines 72–77), which omits any criterion covering `testing-project/` source.

**Suggestion:** Add one observable behavior-preservation criterion covering the reformatted `testing-project/` source — at spec altitude, an outcome not a mechanism. The cleanest fit is the already-documented check, e.g.: "Given the reformatted tree, when `npm --prefix testing-project run check:config` is run, then it succeeds (the reformatted `testing-project/` config and its import graph still load)." (Phrase it as the observable outcome — the config loads with no config-load/import regression — rather than mandating that exact command if the owner prefers; but the spec must pin *some* observable guarantee to this surface.)

**Why it matters:** Req 5 made a deliberate scope decision to reformat generated and fixture files uniformly rather than carve them out. That decision is only safe if "no behavioral change" is *demonstrable* across the whole expanded surface — which is exactly the principle the iteration-1 review established (and the revision honored for lockfiles). Leaving `testing-project/` source as reformatted-but-unchecked is an internal inconsistency in how the spec discharges its own "no behavioral change" guarantee, and it leaves a real reformatted surface (TypeScript that the repo's typecheck/test do not touch) with no acceptance test a downstream author could write. A documented check fits perfectly, so closing the gap is a one-line tightening, not a direction change.
