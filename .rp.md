# Radical Pipelines conventions

This file captures project conventions for [Radical Pipelines](https://github.com/Automattic/radical-pipelines). Future runs of the skill read this file and skip setup if all required conventions are present.

## Pipeline base slug

Format: `<gh-issue-id>-<short-description>`.

- `<gh-issue-id>` is the number of the GitHub issue the pipeline tracks (no `#`).
- `<short-description>` is lowercase, hyphen-separated, no spaces.
- Example: `42-create-docs`.

Forks append `-v<N>` (N ≥ 2): `42-create-docs-v2`, `42-create-docs-v3`, …

## Artifact folder

Each pipeline's artifacts live under `.pipelines/<pipeline-slug>/` at the project root, with one subfolder per phase (`0-prompt/`, `1-spec/`, `2-design-doc/`, `3-plan/`, `4-code/`, `5-docs/`).

## Artifact storage

Mode: `artifacts-in-repo`. The project-root `.rp.md`, each pipeline's `.pipelines/<pipeline-slug>/` folder, and any related `.gitignore` entries are committed directly to `Automattic/skillsmith` alongside the code.

## Commit format

`<commit-description> (<agent-name>)` — imperative mood, sentence case, no trailing period. The orchestrator counts as an agent (`orchestrator`).

Examples:

- `Add spec.md (spec-writer)`
- `Approve design doc (design-reviewer)`
- `Implement scenarios loader (code-writer)`
- `Add .rp.md (orchestrator)`

## Issues

The project's public-facing issue tracker is **GitHub Issues** in `Automattic/skillsmith`, accessed via the `gh` CLI. Each pipeline's canonical prompt and discussion live there.

Internal progress tracking is mirrored to **Linear**:

- Team: `Billow` (key `BILLOW`) — required as the `team` argument when creating a Linear issue.
- Project: `Billow Pipelines` — pass this exact display name (or the stable UUID `a5ca0058-ae66-4381-b808-9bee93535ade`) as the `project` argument. Do **not** pass the URL slug `billow-pipelines` or the slug suffix `15a89be6fe3c`: neither resolves, and the create call then silently succeeds with **no project attached**. URL: `https://linear.app/a8c/project/billow-pipelines-15a89be6fe3c`.
- Access: Linear MCP server (`mcp__linear-server__*`).
- **Verify after every create/update:** the returned issue must include a non-empty `projectId` (and the expected labels and status). If `projectId` is missing, the project reference failed to resolve — re-apply it with the display name or UUID before continuing.

Phase tracking uses Linear **status** (custom statuses, already configured in the project):

- `0 - Prompt`
- `1 - Spec`
- `2 - Design Doc`
- `3 - Plan`
- `4 - Code`
- `5 - Docs`
- `PR opened`

Labels applied to the Linear issue:

- `skillsmith` — always set.
- `v<N>` — exactly one version label per Linear issue, reflecting the latest fork (`v1`, `v2`, `v3`, …). If a `v<N>` label does not exist in the project, create it on demand.
- `running…` — set while an autonomous run is in progress; removed on successful close-out, owner interruption, or unrecoverable failure.

### Resolving a task reference

When the owner asks to work on a task without a URL or ID, the orchestrator must search both trackers before treating the task as new — `gh issue list --search "<keywords>" --state all` in `Automattic/skillsmith`, and the `billow-pipelines` Linear project filtered on the `skillsmith` label. Surface plausible matches (title, ID, state, URL) to the owner and ask which one — if any — is the intended task. Only if nothing matches and the owner confirms the task is new, fall through to Entry C.

### Entry points

A pipeline is always anchored to one GitHub issue **and** one Linear issue (the mirror). A GitHub URL or `#<n>` selects Entry A; a Linear URL or `<TEAM>-<n>` selects Entry B; anything else runs "Resolving a task reference" first.

**Entry A — GitHub-first.** The reference is an existing GitHub issue.

1. Search the `billow-pipelines` Linear project for an issue already linking to this GitHub issue (URL attachment, body link, or matching title). If found, reuse it.
2. Otherwise create a new Linear issue: title and short summary from the GitHub issue, attach the GitHub URL.
3. Apply the `skillsmith` label and the `v<N>` label matching the pipeline. Set the status to `0 - Prompt`.

**Entry B — Linear-first.** The reference is an existing Linear backlog item.

1. **Dedup against GitHub.** Search GitHub Issues for an issue that links to this Linear item (URL in body/comments) or has a matching title. If found, switch to Entry A — the Linear item is already the mirror.
2. Read the Linear item's title and description; draft a GitHub-facing issue body from it. Because GitHub is public and Linear is often internal, **always ask the owner to approve or edit the draft before creating anything — including in autonomous mode**.
3. Create the GitHub issue with `gh issue create` using the approved content.
4. Attach the GitHub URL to the existing Linear item (do **not** create a new Linear issue); add a link to the Linear URL in the GitHub issue body or first comment.
5. On the existing Linear item, apply the `skillsmith` label (if missing) and the `v<N>` label. Set the status to `0 - Prompt`.

**Entry C — from scratch.** Neither a GitHub issue nor a Linear item exists yet. Ask the owner to create one in either tracker, then resume at Entry A or B. The orchestrator does not invent the starting issue.

### Linear update rules

The Linear issue's **status** tracks the latest pipeline phase. On every phase transition, set the status to match the phase the pipeline is currently in — the active phase if one has started, otherwise the highest completed phase. If a phase fails or is aborted, the status stays on that phase until the pipeline either retries it or moves on. The status always reflects the current pipeline state, even when the workflow moves back to an earlier phase.

When the orchestrator opens the pull request for the pipeline, set the status to `PR opened` — the terminal status for a successful pipeline.

When a fork is created, replace the existing `v<N>` label on the shared Linear issue with the new version's label, keeping exactly one version label at all times.

The canonical issue body and all discussion live on GitHub. Linear is a status mirror; comments there are optional.

## Worktrees

All work for a pipeline happens inside a Claude Code worktree. Never modify files in the main working directory, never use raw `git worktree`, and never `cd`.

- **Create and enter:** `EnterWorktree({ name: "<pipeline-slug>" })`. Creates the worktree at `.claude/worktrees/<pipeline-slug>` and enters it. All subsequent tool calls and spawned agents inherit the worktree as their working directory.
- **Re-enter an existing worktree:** `EnterWorktree({ path: ".claude/worktrees/<pipeline-slug>" })`.
- **Exit:** `ExitWorktree`.

## Branch names

Branch names are derived automatically by `EnterWorktree` from the worktree name. Do not choose branch names independently and do not rename branches after the fact.

- **Format:** `worktree-<pipeline-slug>`.
- **Source of truth:** the `name` passed to `EnterWorktree` (equal to the pipeline's versioned slug) determines the branch.

## Branch publishing

The orchestrator publishes the pipeline branch to `origin` (`Automattic/skillsmith`) **automatically on every commit** so teammates can follow status and progress in real time — not only at phase boundaries.

- **First push (sets upstream):** `git push -u origin worktree-<pipeline-slug>`. Run this the first time the worktree has a commit to publish.
- **Subsequent pushes:** `git push` from inside the worktree, **after every commit** the orchestrator or a spawned agent makes. Spawned-agent prompts must instruct the agent to push immediately after each commit it authors.
- **Never push to `trunk`** (the project's main branch); only pipeline branches (`worktree-*`) are pushed.
- **Failure handling:** if `git push` fails (auth, network, non-fast-forward), retry once. If it still fails, surface the error to the owner and continue local work — do not block commits on a failing push. **`--force-with-lease` is never the automatic recovery here**; on a non-fast-forward, surface and stop.
- **Never force-push** the branch on the orchestrator's own initiative. `--force-with-lease` is permitted only when the owner explicitly asks for a rewrite (e.g., a rebase) in the same session; warn the owner before running it.

## Team spawning

Every autonomous workflow that spawns agents must use exactly one Claude Code team using `TeamCreate({ name: "<pipeline-slug>" })`.

Agents in the same team address each other directly via `SendMessage({ to: "<agent-name>", ... })`. When a phase reference says two agents exchange messages, the orchestrator does not relay between them by default. It only spawns, monitors, and waits for completion signals.

If an agent-to-agent message fails (e.g. the target agent is unreachable, errors out, or stops responding), the orchestrator may step in to investigate and try to recover — for example, by re-delivering the message, restarting the affected agent, or relaying directly as a fallback. Intervention is for repair only; once the exchange is healthy again, the agents resume talking to each other directly.

## Health monitoring

Use Claude Code's bundled `/loop` skill — no install is required. Only the autonomous workflow launches the monitor; assisted runs do not.

- **Start:** `/loop 5m <prompt>` where `<prompt>` is the template from `reference/health-monitoring.md`.
- **List active loops:** `/loop-list`.
- **Cancel:** `/loop-kill <id>` using the id returned at start.

The orchestrator starts the loop itself; the owner is not asked to run the command. Cancel the loop on run close-out and after any owner-requested interruption.
