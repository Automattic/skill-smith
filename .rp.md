# Radical Pipelines conventions

This file captures project conventions for [Radical Pipelines](https://github.com/Automattic/radical-pipelines). Future runs of the skill read this file and skip setup if all required conventions are present.

## Pipeline base slug

Format: `<gh-issue-id>-<short-description>`.

- `<gh-issue-id>` is the number of the GitHub issue the pipeline tracks (no `#`).
- `<short-description>` is lowercase, hyphen-separated, no spaces.
- Example: `42-create-docs`.

Forks append `-v<N>` (N ≥ 2): `42-create-docs-v2`, `42-create-docs-v3`, …

## Artifact folder

Each pipeline's artifacts live under `.pipelines/<pipeline-versioned-slug>/` at the project root, with one subfolder per phase (`0-prompt/`, `1-spec/`, `2-design-doc/`, `3-plan/`, `4-code/`, `5-docs/`).

Artifact storage mode: `artifacts-in-repo`. Everything is committed directly to this repository alongside the code.

## Commit format

`<commit-description> (<agent-name>)`

Examples:

- `Add spec.md (spec-writer)`
- `Approve design doc (design-reviewer)`
- `Implement scenarios loader (code-writer)`

When the orchestrator commits on its own (no agent), the `(<agent-name>)` suffix is omitted: `Add .rp.md`.

## Issues

The project's public-facing issue tracker is **GitHub Issues** in `Automattic/skillsmith`. Each pipeline's canonical prompt and discussion live there.

Internal progress tracking is mirrored to **Linear**:

- Project: `billow-pipelines` (`https://linear.app/a8c/project/billow-pipelines-15a89be6fe3c/overview`).
- Static label (always set): `skillsmith`.
- Version labels (one per pipeline, already created): `v1`, `v2`, `v3`, …
- Phase labels (already created): `0 - Prompt`, `1 - Spec`, `2 - Design doc`, `3 - Plan`, `4 - Code`, `5 - Docs`.

Access Linear via whichever interface is available — the Linear MCP server (`mcp__linear__*`) or the Linear CLI. Do not enforce one. Access GitHub via the `gh` CLI:

- Read: `gh issue view <id>`
- Comment: `gh issue comment <id> --body "..."`
- Create: `gh issue create --title "..." --body "..."`

### Entry points

A pipeline is always anchored to one GitHub issue **and** one Linear issue (the mirror). How they come into being depends on what the owner points the orchestrator at.

**Detection.** A GitHub URL or `#<n>` selects Entry A. A Linear URL or `<TEAM>-<n>` selects Entry B. If the reference is ambiguous or absent, ask.

**Entry A — GitHub-first.** The owner points to an existing GitHub issue.

1. Search the `billow-pipelines` Linear project for an issue that already links to this GitHub issue (URL attachment, body link, or matching title). If found, reuse it — skip step 2.
2. Otherwise create a new Linear issue in the project, copy the title and a short summary from the GitHub issue, and attach the GitHub URL.
3. Apply the `skillsmith` label, the version label (`v1` for a first pipeline, `v<N>` for the Nth fork), and the appropriate phase label.

**Entry B — Linear-first.** The owner points to an existing Linear backlog item.

1. Read the Linear item's title and description.
2. Draft a GitHub-facing issue body from it. Because GitHub is public and Linear is often internal, **always ask the owner to approve or edit the draft before creating anything — including in autonomous mode**.
3. Create the GitHub issue with `gh issue create` using the approved content.
4. Attach the GitHub URL to the existing Linear item (do **not** create a new Linear issue) and add a link to the Linear URL in the GitHub issue body or first comment.
5. On the existing Linear item, apply the `skillsmith` label (if missing), the version label, and the phase label.

**Entry C — from scratch.** Neither a GitHub issue nor a Linear item exists yet. Treat as Entry A after the owner authors a GitHub issue first, or as Entry B after the owner creates a Linear backlog item first — the orchestrator does not invent the starting issue on its own.

### Linear update rules

The phase label reflects the **latest run status only**. On every phase transition, remove the previous phase label and apply the label of the phase the pipeline is currently in — the active phase if one exists, otherwise the highest completed phase. The Linear issue always carries exactly one phase label, even when the workflow moves back to an earlier phase.

The canonical issue body and all discussion live on GitHub. Linear is a status mirror; comments there are optional.

## Worktrees

All work for a pipeline happens inside a Claude Code worktree. Never modify files in the main working directory, never use raw `git worktree`, and never `cd`.

- **Create and enter:** `EnterWorktree({ name: "<pipeline-slug>" })`. Creates the worktree at `.claude/worktrees/<pipeline-slug>` and enters it. All subsequent tool calls and spawned agents inherit the worktree as their working directory.
- **Re-enter an existing worktree:** `EnterWorktree({ path: ".claude/worktrees/<pipeline-slug>" })`.
- **Exit:** `ExitWorktree`.

## Branch names

Branch names are derived automatically by `EnterWorktree` from the worktree name. Do not choose branch names independently and do not rename branches after the fact.

- **Format:** `worktree-<pipeline-slug>`.
- **Source of truth:** the `name` passed to `EnterWorktree` (equal to the pipeline's versioned slug) determines the branch.

## Branch publishing

By default, the orchestrator pushes the pipeline branch to `origin` (`Automattic/skillsmith`) so other contributors can inspect ongoing pipelines and their status.

- **First push (sets upstream):** `git push -u origin worktree-<pipeline-slug>`.
- **Subsequent pushes:** `git push` from inside the worktree. Push after each phase-completion commit so the public state matches the local one.
- The orchestrator does **not** push to `trunk` (the project's main branch); only pipeline branches are pushed.

## Team spawning

Every autonomous workflow that spawns agents must use exactly one Claude Code team using `TeamCreate({ name: "<pipeline-slug>" })`.

Agents in the same team address each other directly via `SendMessage({ to: "<agent-name>", ... })`. When a phase reference says two agents exchange messages, the orchestrator does not relay between them by default. It only spawns, monitors, and waits for completion signals.

If an agent-to-agent message fails (e.g. the target agent is unreachable, errors out, or stops responding), the orchestrator may step in to investigate and try to recover — for example, by re-delivering the message, restarting the affected agent, or relaying directly as a fallback. Intervention is for repair only; once the exchange is healthy again, the agents resume talking to each other directly.

## Health monitoring

Use Claude Code's bundled `/loop` skill — no install is required. Only the autonomous workflow launches the monitor; assisted runs do not.

- **Start:** `/loop 5m <prompt>` where `<prompt>` is the template from `reference/health-monitoring.md`.
- **List active loops:** `/loop-list`.
- **Cancel:** `/loop-kill <id>` using the id returned at start.

The orchestrator starts the loop itself; the owner is not asked to run the command. Cancel the loop on run close-out and after any owner-requested interruption.
